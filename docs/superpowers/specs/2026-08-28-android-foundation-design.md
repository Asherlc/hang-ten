# Hang Ten Android Foundation Design

## Goal

Deliver a native Android application that gives athletes the core Hang Ten
coaching experience using the repository's canonical board packages and plan
library without creating a second source of board geometry or routine content.

## Scope

The Android foundation includes:

- Kotlin and Jetpack Compose application setup suitable for Android 10 (API
  29) and newer.
- Build-time staging of the existing `Hangboards/` packages and
  `HangTen/Resources/PlanLibrary.json` into Android assets without changing
  their bytes.
- Strict Kotlin decoding for the consumed board and plan schema, failing closed
  for malformed bundled content.
- A board picker and plan picker backed only by that staged content.
- Canvas rendering of presentation images and canonical normalized hold paths;
  an active workout highlight renders the same decoded path that is used for
  hit testing.
- A pause-safe workout session based on monotonic elapsed time, including a
  three-second start countdown, active-step progress, pause/resume, completion,
  and local session history.
- Bundled countdown audio and Android text-to-speech for instructional cues,
  gated by an explicit user setting.
- Unit tests for decoders, hold-target resolution, and workout clock behavior;
  Compose tests for the core navigation/session flow.
- Full Android CI/CD: deterministic Gradle wrapper builds, static analysis,
  JVM and instrumented emulator tests, pull-request APK artifacts, release
  Android App Bundles, and guarded publication to the Google Play internal
  track.

The foundation deliberately excludes Google Play Billing, Health Connect,
GitHub board editing and sync, analytics/crash reporting, and live Bluetooth
force sensors. Each is a distinct Android integration that follows after the
core experience is usable and device-tested.

## Architecture

`Android/` is a standalone Gradle project. It owns Android-specific UI and
runtime adapters; the existing iOS target stays untouched. A small Kotlin
domain layer decodes the portable JSON documents and defines the immutable
board, plan, and workout-timeline models. Repositories load only bundled
assets during this milestone. DataStore retains the selected board, cue
preference, and completed-session history.

Compose screens consume state from lifecycle-aware view models. The workout
view model is the sole owner of session state. It derives each render from a
monotonic clock so recomposition, rotation, and UI scheduling cannot advance
the routine incorrectly. While the app is not foregrounded, the session pauses
and audio is cancelled; resuming remains an explicit athlete action.

`BoardCanvas` maps normalized board coordinates to the displayed presentation
rectangle. It supports the existing `roundedRect` and path commands (`move`,
`line`, `quad`, `curve`, `close`), applying each hold geometry frame before
drawing. The exact decoded geometry is used for both highlight and tap testing.

## Shared Content Contract

The Python package validator remains the authoritative repository validation
for board content. Android consumes files generated by one deterministic Gradle
copy task rather than copies committed beneath `Android/`. The task stages
only `board.json`, referenced presentation image files, the plan library, and
reviewed countdown audio. It must reject an absent referenced asset and expose
the staged inputs to Android unit tests.

Android target resolution matches the portable plan vocabulary against holds
in the selected board. It may choose equivalent holds from supported metadata,
but it must never manufacture hold IDs, dimensions, or coaching instructions.

## UX

The initial app has three bottom-navigation destinations:

- **Train:** selected board, favorite/default plans, and launch action.
- **Plans:** board picker and browsable available plan library.
- **History:** local completed sessions in reverse chronological order.

The workout screen is distraction-light: board image and highlighted holds,
current task, elapsed/remaining duration, and pause/end controls. It supports
portrait and landscape through responsive Compose layout without maintaining
separate session state.

## Runtime Boundaries

Audio is an Android adapter behind a small interface. The countdown sound pack
is bundled and scheduled against the same monotonic timeline as visual state;
late callbacks must be discarded rather than played late. Text-to-speech is
best-effort and must never block the clock.

The foundation does not request Bluetooth, health, account, or billing
permissions. Those are introduced only when their corresponding feature is
implemented behind a user-initiated action.

## CI/CD and verification

The existing change-classification workflow gains Android and shared-content
paths. Android-relevant pull requests run Gradle wrapper verification on Linux:
the staged-content check, JVM unit tests, Android lint, a Debug APK build, and
Compose instrumented tests on an API 35 emulator. The workflow uploads the
Debug APK and reports on failure as review artifacts.

A protected `google-play` GitHub environment owns release publication. A push
to `main` builds a Release AAB; an approved release workflow signs it using an
upload keystore decoded only into runner-temporary storage and publishes it to
the Play internal track through a least-privilege Google service-account
credential. It fails closed when the required environment secrets/variables are
absent, never prints them, and retains the AAB as an artifact. The initial
repository change cannot provision the Play Console app, signing key, or Google
Cloud service account; the README documents the exact operator handoff.

The staging task is exercised in CI and the existing Python board validator
remains part of repository validation. Before declaring the milestone complete,
install and visually inspect the APK on an Android emulator in portrait and
landscape.

## Follow-on milestones

1. Google Play Billing and restore behavior.
2. Health Connect write/read integration with an explicit Connect action.
3. BLE force-sensor transports, starting with deterministic parser/transport
   fixtures and then physical hardware validation.
4. Board package editing and GitHub device-flow sync.
